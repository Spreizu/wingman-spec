# Changelog

Versions are git tags on `main` (`v0.5.0`, `v0.6.0`, ...).

## 0.11.2

- **Shorter, concrete instructions.** The shipped prose (schema, templates, commands, agents, partials, config template, `AGENTS.md` block, skills, docs) follows ten writing rules: one instruction per sentence, numbers instead of "several", no hedges, lists instead of chained clauses. Every operational instruction is kept. Measured with `scripts/prose-lint.cjs --metrics` on the same files: sentences of 30+ words 265 -> 167, of 45+ words 80 -> 31, mean sentence 15.7 -> 13.4 words, lines with 2+ parentheses 154 -> 95, lint warnings 571 -> 339; the rewritten files are 386 words shorter. No shipped sentence is above 60 words (`tests/drift.sh` fails on one).
- **New first-party skill `spec-writing`.** The rules for requirements, scenarios and proposals, with a before/after example: a THEN names a value a test can check, not "handled correctly". The schema and `/spec-propose` load it where specs are written; `install.sh` copies it with the others.
- **Prose lint.** `scripts/prose-lint.cjs` (repository tool, warn-only; `--strict`, `--json`, `--metrics`) checks long sentences, vague words, stacked parentheses and semicolons; it skips code, quoted words, YAML keys and template placeholders. `verify-task lint` adds an info finding (`vague-then`) for a THEN/AND line with a vague result ("handled gracefully", "works as expected") and no quoted value, number or code. Tests: `tests/prose-lint.sh`.
- **Clearer verifier messages.** The size cap names the fix ("Merge tasks that touch the same files ... or set Size: M"), a visual scenario without `component:` says how to add one, and the UI-task lint asks for `Visual: <scenario id>`.
- **Faster defaults, every fault still caught by `finish`.** Measured on the synthetic 5-task change (tests 20 s): `Check level: targeted` is the default (42 s instead of 140 s with one task per dispatch). Each check runs only the task's targeted tests: test files the change added or edited, tests tagged with the task's scenarios, tests named after the task's files or any source file the change edited. They run through `- Targeted test command: <runner> {files}` or a template derived from the test command (vitest, jest, mocha, ava, node --test, pytest, rspec, deno, bun, go); when none is known the check says so and runs no tests. Typecheck and lint run at the check that ends a task group (`tsc --incremental`, `eslint --cache` from `install.sh`: 3.0 s -> 1.3 s for a leaf edit on 1,500 files), the full suite at a review task and once at `finish`. With a 60 s suite a 5-task change takes 66 s (`Check level: group` 126 s, `task` 307 s). A break in a test no task targets is now found at `finish`; a break in a targeted test is still found at the check. Tests: `tests/targeted.sh`. `visual.scope: task` is the default: a task's check opens its own scenarios and `finish` checks every other declared scenario against the state before the change (55 s and 56 captures instead of 120 s and 150). `visual.changed_only: on` (an identical passing visual run is not repeated; never for a scenario with a `role:`, whose login depends on credentials and env vars) and `visual.request_timeout: 3` (8.9 s instead of 10.9 s on the noisy page) are defaults; `visual.baseline` stays off. Opt-ins for the stricter per-task gate: `- Check level: group` or `task`, `visual.scope: all`, `visual.changed_only: off`, `visual.request_timeout: 0`.
- **`next` on a large repo: 40.7 s -> 0.35 s.** The working-tree hash ran `git add -A` into a temporary index: every untracked, not ignored file was read and written into `.git` (a 1.7 GB docker data directory next to the code: 40.7 s for the first `next`, 31.8 s for the first `check`, `.git` grew by 1.7 GB). Now the hash copies the real index (its stat cache: only changed tracked files are read), runs `git add -u`, and adds untracked files by name, size and mtime; ignored files stay out. One hash per process and scope; a new run no longer hashes at all, and only the review task builds a snapshot commit. The fast-path line count skips untracked data (binary, over 512 KB, or older than the change's first run). Measured on 50,066 tracked files, 20,000 ignored files and 51,500 untracked files (1.7 GB): `next` 0.35 s, `check` 1.6 s, `finish` 0.9 s (was 4.7 s), `.git` unchanged. The new-run line reads "new run <id> (session s) on main at <commit> in <dir>". Tests: `tests/next-perf.sh`.
- **Timeline of a build.** Every `verify-task` step appends one line to `openspec/.apply-runs/<change>/timeline.jsonl` (run start, task picked, check start and result, fix round, tick, review, finish, sync, archive; local time, session, duration, short details). Plan edits made during the build (requirements, Why, scenarios, task lines, ADRs, `design.md`) become a `decision` line with what changed and the reason (`--reason`, a `Decision:` line, or the added ADR); a changed Why or a removed requirement records the owner approval or `missing`. `archive` keeps the file with the archived change. See [docs/timeline.md](docs/timeline.md). Tests: `tests/timeline.sh`.
- **What moved.** The 3 seeded regressions in another spec's scenario (hidden count, page scrolling sideways, demoted heading) are caught at `finish` instead of at the task's check; with `visual.scope: all` at the check again (both tested in `tests/verify-task.sh`, 15/15 faults). A test break in a task that does not end its group is found at the group's last check. See [docs/speed.md](docs/speed.md).

## 0.11.1

- **No commits during a change.** `/spec-apply`, `/spec-fix` and `/spec-archive` no longer tell the agent to commit (a commit per task, a commit of the fix, a commit of the archive move); the archive result no longer suggests one. `AGENTS.md` states the rule once: agents never commit, stage, stash, reset or switch branches, and the whole change stays in the working tree for you to review and commit (once, or in chunks). The verifier never depended on a commit: run records, `finish` freshness, the result cache, the anchor guard and Branch Review all work on a dirty tree (new test in `tests/apply-runs.sh`: finish and `next` on an uncommitted tree, and a commit afterwards keeps the finish valid). See [docs/no-commits.md](docs/no-commits.md), including how to commit so stale-anchor drift stays quiet.
- **Code review needs no commits.** The review task's `next` packet (JSON and prompt) carries `review_range`: `BASE_SHA` (the commit the run started from) and `HEAD_SHA` (an unreferenced snapshot commit of the working tree, built from a temporary index without touching the index, branch, HEAD, stash or `git log`); the implementer uses them instead of `git rev-parse HEAD~1`, and the prompt no longer says the orchestrator commits. Nothing in the flow creates a commit. See `docs/no-commits.md`.
- **Neutral examples.** Example selectors, component and capability names in the visual-check header, the spec template, the schema and the tests are generic (`result-card`, `list-item`, `empty-state`, `search`, `ResultList`, `list-search`). Test fixtures, prompts and docs use neutral names: capability `app`, route `/gallery`, sample project `helpdesk`, "Users" in Why lines, "highlighted" in the design-map example.
- **`check` and `finish` run the project's commands once, and say what they are doing.** Measured on a 4,400-file project with 300 requirements and a 20-second test command (the suite is the fixed part): a Size S batch of two tasks naming the same test command took 41.4 s in 0.11.0 (the command ran once per task, uncached) and takes 21.3 s; `finish` after the checks took 20.8 s and takes 0.9 s (the `Done when:` run now writes the result cache that `finish` reads); `sync` 8.5 s -> 0.3 s and `archive` 8.9 s -> 0.8 s (they no longer run the blame-based stale-anchor drift, which `drift` still prints; its blame results are cached in the git directory, so a second `drift` takes 0.35 s instead of 8 s). A stale-cache negative is tested: an edit between `check` and `finish` runs the command again, a tick or a `tasks.md` edit does not, a failing result is never reused. `--timing` / `SPEC_PROFILE=1` prints what each command and scan cost, most expensive first, and records it in `metrics.jsonl`; a command running for 3 s or more is announced on stderr with its elapsed time (then every 15 s); `SPEC_TIMEOUT_<TESTS|TYPECHECK|LINT|DONE_WHEN|VALIDATE>` limits one command. New, opt-in and a project owner's decision: `- Test run: finish` in the config (or `SPEC_TEST_RUN=finish`) runs the whole project suite once at `finish` instead of at every `check`; it drops the per-task regression gate, so the default is unchanged. What remains is the project's own suite time. See [docs/speed.md](docs/speed.md).
- **A visual check on a page with defects that are not the task's is faster and no longer blind.** A request that never answers kept the load from completing, so every state at every width waited 5 s, then 5 s for the network to idle, and then reported only "could not open" without running any check on the page. Measured on a page with 80 failing images, 3 images that never answer, console errors, axe violations and overflow (one scenario, 3 states x 3 widths): 31.3 s in 0.10.3 and 0.11.0, 10.9 s now, 7.2 s with `visual.request_timeout: 1`. The first state waits once and names what it waits for, the checks run on the page as it stands (the axe, overflow and key-element defects behind it are now found: 1,030 -> 1,071 reported), later captures abort that URL at once, and a request or console error repeated in a later state of the same viewport is reported once (counted in `perf`). New config: `visual.page_timeout` (default 5 s), `visual.request_timeout` (default off), and opt-in `visual.baseline: on`: a request, HTTP, console or axe defect that the capture before the task already had, and an axe defect outside the key elements, is listed once with a count and does not fail the task, while new defects, key-element defects, overflow, broken images and every scenario expectation still fail; the default keeps every defect failing. Tests: `tests/visual-noisy.sh`.
- **How often tests and the visual check run (audit, and opt-in levels).** On a 5-task change the project's commands ran 5 times each per-task (142 s on the synthetic project) or 2 times with one dispatch per task group (60 s); the cache skips only identical repeats. New and opt-in, default unchanged, each a project owner's decision: `- Check level: group | finish` (or `SPEC_CHECK_LEVEL`) runs tests, typecheck and lint once per group or once at `finish` (63 s and 30 s for the 5 tasks; `Done when:` and the static scans still run per task, a review task always runs everything); `visual.scope: task` checks a task against its own scenarios and leaves the earlier ones and the guards to `finish` (54 s instead of 122 s on a 5-task UI change, 56 captures instead of 150); `visual.changed_only: on` / `--changed-only` skips an identical passing visual run when the pages' files are unchanged (a changed test, Markdown or tests/ file does not count). Tests: `tests/runfreq.sh`, `tests/visual-cache.sh`. See [docs/speed.md](docs/speed.md).
- **Anchor count is no longer a finding by itself.** `anchor_fit` reports it only above `anchor_max` (default now 6) and only when some anchors are weak (a finding of their own, or two markers in one function), naming the weak ones once; anchors that each fit are never flagged or pruned for the count, one info line above 12 asks whether to split the requirement, and `Anchors: many` in a requirement or `anchor_many: [cap/slug]` in the config skips it (also for the guard's `anchor-sprawl`).
- **Archives, changes and run records are ordered by time, not by day.** `openspec archive` names the folder with the day only, so same-day archives sorted by name. The archive step now writes `archived.json` (`archived_at` to the second with the UTC offset, `created_at` when known) in the folder; one helper (`chronology.cjs`) orders archives, replay, runs and the changes list by it, falling back for folders without it to the git commit time, then the modification time, then the date in the name (no migration, ties by name).

## 0.11.0

A lighter workflow with the same gates. Measured against v0.10.3 on four pre-written plans (acceptance, traps and mutation scores identical, no fix rounds): a Size S change takes 1 dispatch instead of 3, 24 to 28% fewer artifact words and 41% fewer instruction tokens; a Size M UI change takes 2 dispatches instead of 3 and 38% less script time. Numbers and method: [docs/fast-path.md](docs/fast-path.md).

- **Fast path.** `Size: S` + `Risk: none` + no sensitive path + no UI + no dependency manifest needs no `design.md`, no `adrs/none.md`, no agent-written app-map (`verify-task.cjs app-map <change> --apply` writes the two lines) and no `progress.md`. `check` and `finish` upgrade a change to the full path when the edits touched a sensitive path, a UI file, a manifest, or more than 150 lines. See [docs/fast-path.md](docs/fast-path.md).
- **The verifier ticks the task box** when a check passes; the implementer no longer edits `tasks.md`. This removed the most common first failure (a wrongly ticked or unticked box). `check` reports the progress after its own tick.
- **One implementer per dispatch.** Size S: the whole change in one dispatch; M/L: one task group; a review task alone; `--per-task` restores one task per dispatch. `check` runs the `Done when:` command of every member and the project checks once.
- **Review task only where it pays**: Size M/L, a Risk kind, or UI. A leftover review task on a fast change is a lint warning.
- **Result cache.** Tests, typecheck and lint that passed in `check` are not run again in `finish` for the same tree and command; independent `finish` steps run in parallel. `--no-cache` / `SPEC_NO_CACHE=1` turns it off. See [docs/dispatch-and-cache.md](docs/dispatch-and-cache.md).
- **Explore and propose look in the repo first** and ask the user only what the repo cannot answer.
- **One statement per rule** across `AGENTS.md`, commands, agents and schema (placement and accessible-name rules live in the implementer agent).
- **Smaller repo.** Five unused extension exports removed; the workspace-layout walkthrough moved from the README to [docs/workspace-layout.md](docs/workspace-layout.md) (README 758 -> 334 lines).

## 0.10.3

- **`verify-task` works with OpenSpec 1.7.x.** That version's `openspec instructions apply --json` gives each task only `id` (a running number), `description` (the whole checkbox text, label included) and `done`: no `line`, no `sourcePath`. `next` stored no line, the task's `Done when:` / `Spec:` details were silently read as empty, and `check` then did not recognise the checkbox. One helper (`resolveTaskLines`) now finds every task's file and line: the given `line` when there is one, else the checkbox with the same text (whitespace-normalised, then without its "1.1" label), duplicates taking the first match nobody used yet, then the checkbox that starts with the task's label. It serves the ledger replay, `next` and `check` (also for a run opened without a line). A task that matches nothing is refused with a message naming it; nothing continues with line 0. New `tests/task-lines.sh` (a shim that strips the fields from the real output, duplicates, regex characters, several task files, the recorded 1.7.0 output).
- **`ignore-http:` also skips the console error a failed load leaves behind.** Chromium words it `Failed to load resource: the server responded with a status of 404 ()` (also 403, 500, `net::ERR_*`), with no URL in the text, so the URL pattern never matched. It is now matched by the URL the browser reports for the message (Playwright `msg.location().url`); when there is none, it is skipped if the page skipped a failed request with the same status or `net::` error; a failed load whose URL matches no pattern is still reported, also when another URL on the page was skipped. The ignored list names the pattern that skipped each one.
- **State steps: a control that is hidden at one viewport no longer fails the whole state.** States run at several widths, and a menu toggle that exists but is hidden at desktop widths made `do: click ...` fail there. A `click` or `hover` whose target exists in the page but is not visible is now skipped at that width, with an info note (`step skipped: <target> exists but is hidden at 900px`) listed in the report next to the ignored defects. A target that matches nothing, or a visible one that cannot be clicked (covered, disabled, timeout), still fails. `do: click! <target>` (and `hover!`) is the strict form: it fails when the control is hidden. `fill`, `press`, `storage`, `goto` are never skipped. A state has no `viewports:` of its own (only the scenario does); not added.
- **Extension, Tasks tab.** The highlighted `next` task fills its card edge to edge (one surface with its Done-when lines; a leftover generic `.next` style had inset it), long words in task titles wrap inside the card, and an empty group shows no `0/0`. Inline code in task, requirement, scenario and ADR text renders as `<code>` everywhere it reaches a page, and tree labels, tooltips, quick picks and hover text show it as plain text without backticks. New tests: `test/browser/task-rows.mjs` (row box equals the card content box within 1px at 375 and 900px, light and dark, 0/1/many tasks) and `test/taskText.test.ts` (no backtick in any rendered page).

The unit tests moved out of the script into `tests/fixtures/anchorfit/unit.cjs` (translation layouts, a real-logic negative, stacked markers); the extension reads the same script, so it gets the same behaviour.

Now a none record is read by one function, `isNoneAdr(fileName, text)` in `quality.cjs`, which the scripts and the extension both use: it is a none record when the file is named `none.md`, or its front matter says `status: none` (any case), or both. All three now use `isNoneAdr`.
- **Tests.** A change with only `none.md` shows no ADR pill and a zero count (change page, History card, archived page); one with `none.md` plus a real ADR shows "1 ADR". The parity test runs the script's and the editor's definition on the same cases.

## 0.10.0

- **No more intents layer: every requirement says who wants it and why.** A requirement now has one line directly under its SHALL sentence, before the first scenario: `Why: <who wants it, and why>`. Intent files (`openspec/intents/`), `IN-` ids, `Derives:` lines, `## Intents` in proposals and the journey scenario per intent are removed, and `verify-task.cjs intents` with them. A change set cannot contain an "intent nobody built" or a requirement "without an intent" any more: the only rule left is that each requirement has its Why.
- **Before and after.** Before: `IN-reset-password-flow` (one line that says nothing without context) in `openspec/intents/`, a `Derives: IN-reset-password-flow` line on a requirement, and a scenario `Journey IN-reset-password-flow: ...`. After: the requirement "Reset a forgotten password" carries `Why: The account owner wants to reset a forgotten password, so that they are not locked out.`
- **Lint.** `missing-why` (error) and `why-too-short` (error under 5 words) for every ADDED or MODIFIED requirement, including non-functional ones (the old exemption is gone). `traceability: warn|off` and `SPEC_TRACEABILITY` work as before.
- **Owner approval moves.** It is needed when a change rewrites the Why of a living requirement (MODIFIED, or a RENAMED one with a new Why) or removes one, not for changed SHALL text or scenarios with the same Why. Satisfied by `Owner approval: <name>, <date>` in `proposal.md`; `lint` and `finish` list the requirements as `why_owner_approval`. The check compares with the living spec, so it works before sync: `/spec-sync` lints first, then merges.
- **Sync.** `sync` and `sync-check` are the same read-only check (specs merged, ADRs promoted, anchors, drift). `/spec-sync` no longer writes intent files.
- **Greenfield.** The exploration note, understood.md, capability and slice files and the gate lose their intent fields; the gate checks the Why of every requirement, and the handover table is slice, requirement, why.
- **Editor extension 0.10.0.** Why in the requirement card, hover, code lens, tree and branch review; `missing-why` problems with an "add Why" quick fix; the dashboard blocks the archive for a rewritten or removed Why until the proposal has the approval line. The Intents page and `Reveal Intent` are removed.
- **No migration.** Old `Derives:`/`## Intents` text is not recognised: write a Why on each requirement. Tests rewritten for the Why (`traceability`, `greenfield`, `problems`, `parallel`, extension), and a drift scan keeps the removed terms out of shipped text.

## 0.9.9

- **A run knows its owner.** `run.json` records the session (`--session <id>` or `SPEC_SESSION`), worktree, branch, HEAD, tree hash and start time. `next`, `check`, `review` and `finish` refuse a run another session or worktree started less than 30 idle minutes ago (`run-owned`, exit 2, with the owner's session, commit and start), and `--takeover` adopts it (logged as a `takeover` metric, the open task and attempt are kept).
- **One live command per change.** `lock.json` (pid, session, command, heartbeat every 15 s) refuses a second concurrent `next`/`check`/`review`/`finish` (`busy`). A dead pid or a heartbeat older than 2 minutes never blocks; `--takeover` replaces it.
- **Records say what they were made from.** Each passing check stores run, session, HEAD, branch, worktree, tree hash and the hash of the task's `Files:`. A ticked task whose record came from a commit that is not in this history, with different files, is `unverified-ticks` again (`foreign` names the commit and branch). Normal linear work, amended commits and uncommitted edits stay valid.
- **No more guessing.** Every `next`/`check`/`review`/`finish` result carries `run_status` (new, own, resumed, took over). When all tasks are verified, `next` prints one status line: which run checked the last task, at which commit, whether the tree still matches, and whether a `finish` passed and still holds or is STALE. `finish` writes `finished.json` and says when an earlier finish exists. `status` shows the owner read-only.
- Separate git worktrees keep separate run logs; a shared specs repository (workspace layout) serializes them with the same refusal. The directory layout under `openspec/.apply-runs/<change>/` is unchanged.
- Docs: apply-loop partial (`--session`, `run-owned`/`busy`), AGENTS block (still within its cap), README, `help` header. Tests: `tests/apply-runs.sh` (35 checks).

## 0.9.8

- **Visual checks can skip defects that are not yours.** A scenario's ```visual block takes `ignore: <code>` (repeatable; an exact defect code, or a prefix when it ends in `:`, e.g. `ignore: a11y:` skips every axe rule) and `ignore-http: <substring>` (repeatable; skips `runtime:http-error`, `runtime:request-failed`, `runtime:console-error` and `content:broken-image` whose message contains the text). `visual.ignore` (codes) and `visual.ignore_http` (list) in `openspec/config.yaml` apply to every scenario. For page chrome or third-party widgets that are out of a change's impact.

- **Not a way to hide the scenario's own claim.** Only `a11y:`, `runtime:`, `content:` (as prefixes or exact codes) and `layout:horizontal-overflow` can be skipped. `layout:key-*` (missing, hidden, offscreen), `layout:overlap`, `design:*` (expect), `role:*` (absent, redirect, login), `state:*`, `server:*`, `regression:*` and unknown codes are refused with an error, as are empty values, a bare `:` and an `ignore-http` text under 3 characters. `layout:overlap` is refused on purpose: overlap of key elements is part of what a scenario asserts. Config lists are checked the same way.
- A console error now names the failing resource (`(at <url>)`), so `ignore-http` can match it.
- Docs: schema instruction, README, `config.yaml.tmpl` (commented example), `spec-implementer` and the AGENTS block (still within its cap). Tests: `tests/visual-ignore.sh` (each form, prefix match, config level, listing, refusals, scenario claims still failing, the `next`/`check` path); the extension reads the grammar from the script, `parity.test.ts` covers the new fields and the refusals.

## 0.9.7

- **Over-anchored code.** `@spec` markers were placed on lines that do not implement the requirement (a "login" marker on an i18n string of another feature). `anchorfit.cjs` finds them: more than `anchor_max` (3) code anchors for one requirement, anchors on imports, types, constants, string tables, logging and plain accessors, many requirements in one small unit, anchors in a file that belongs to another capability, and anchors that share no word with the requirement. These are warnings (`anchor_fit: warn|error|off`, or `SPEC_ANCHOR_FIT`); the last code anchor of a requirement is never reported as removable. The checks are heuristics.
- **Fix.** `verify-task.cjs anchors prune [--select file:line,...] [--apply]` removes the listed marker lines only. `drift` shows them as `over-anchored`; `/spec-garden` and the implementer prompt now say: anchor the smallest unit that implements the observable behaviour, one anchor per requirement per code path, never helpers, imports, types, constants, strings or plumbing, never "to be safe".
- **Anchor guard.** Removing an extra marker is accepted while at least one anchor of the requirement remains and its code is unchanged.
- **Editor.** Over-anchored markers show in the code (problems and anchor view) with a quick action "Remove this marker".
- **Tests.** `tests/anchorfit.sh`, and `fit.test.ts` in the extension (including script/editor parity).
- **No misleading "sync first" instruction.** `/spec-archive` syncs first by itself (specs, ADRs, intents) and stops if the sync finds a problem, so nothing tells the user to run `/spec-sync` before it any more: the `finish` result says "Run /spec-archive <change>; it syncs first", the script's refusal says it was called directly and that `/spec-sync` is only for inspecting or fixing a sync problem, and the commands, schema, config template, AGENTS block, installer text and README say the same.
